# Noon ERP 开发模块与审核节点

更新时间：2026-11-21。此表用于组织开发与审核，是业务工作包划分，不要求每项单独建 Maven 模块；需求细节以 PRD、已确认决定和实际代码为准。状态是制定时的判断，开工前以协作入口和代码为准。

| 编号 | 业务模块 | 主要范围 | 当前状态与完成后的审核重点 |
|---|---|---|---|
| M1 | 基础平台与权限 | 若依登录、用户角色、站点授权、版本化参数、审计和汇率 | 用户站点授权和参数基础已实现并测试；业务入口、汇率和整体审计仍待联调。审核普通用户跨站拒绝、超管全站、历史参数不漂移。 |
| M2 | 商品与基础资料 | 店铺/站点/仓库、SKU、Partner SKU 映射、Offer 状态 | 设计已有，实际管理及数据校验未完整交付。审核唯一性、站点归属、商品映射及只读接口边界。 |
| M3 | 供应商与采购 | 供应商、报价历史、采购单、部分收货和采购成本 | 待开发。审核状态流转、部分收货数量守恒、历史价格与采购成本口径。 |
| M4 | 库存、物流与 FIFO | 入库批次、四态库存、调拨/头程/ASN、批次消耗和盘点 | FIFO 出库及红冲内部服务已有局部测试；入库、完整库存/物流及实际入口未完成。审核 C-5 拆批/在途/短少守恒、并发与幂等、FIFO 及成本不重复。 |
| M5 | 订单与退货 | 多来源导入、订单状态、部分妥投/退货、A/B/C 处置 | 入账安全与红冲已有内部服务；端到端和真实平台适配未完成。审核跨站唯一、重传、部分事件、退货累计和 C-2/C-2b 成本及赔偿一次确认。 |
| M6 | 账单、费用与对账 | 周/月账单、费用明细、差异、争议、回款、费用字典 | 待开发。审核重复导入、周/月分离、未匹配行、争议截止及赔偿/广告费用不遗漏或重复。 |
| M7 | 利润与报表 | L1/FIFO 成本、L2 费用池、三档合并、SKU 可选分摊、历史快照 | 需求与原型有基础，真实引擎待开发。审核 C-3 三档并存、默认不分摊、历史重算、币种和费用成本不双计。 |
| M8 | 补货与预警 | 销量/库存指标、建议量、分站点建议、人工确认及转单 | 待开发。审核公式、站点隔离、在途影响与人工确认闭环。 |
| M9 | Noon 集成与数据导入 | 只读 API、CSV/人工导入、事件适配、来源保留和待核对 | 登录及事件类型只读实测通过；真实订单/退货样本与适配未完成。审核真实字段与身份、幂等、权限、保密；不假定已有未证实平台能力。 |
| M10 | AI 建议与审批 | 只读业务视图、AI 草稿、独立角色及人工审批/受控转正 | 用户决定具体 AI 权限待业务接入时配置；尚未实现。审核 AI 与正式数据隔离、独立角色、审核记录和未配置规则不自动通过。 |

## 建议开发顺序与交付节点

这是工作推进顺序，不要求一个模块全部完成后才启动下一个；每一阶段先交付可运行的小闭环，再由 Codex 集中审核。当前代码只是局部基础，不能因为排在前面就视为完成。

| 阶段 | 先做什么 | 交付及审核节点 | 依赖和可并行工作 |
|---|---|---|---|
| 1 | **M2 商品与基础资料**，同时补 M1 必需项 | 可维护店铺/站点/仓库、SKU、Partner SKU 映射；授权用户只能操作获授权站点。审核映射唯一、仓库归属及跨站权限。 | 复用已有登录和站点授权；汇率、审计按接入需要补，不必重写若依。 |
| 2 | **M3 供应商和采购** | 供应商、报价、采购单与部分收货；审核价格历史、数量守恒、成本只含采购价。 | 依赖阶段 1 商品和必要汇率；M9 可并行准备 CSV/人工导入约定。 |
| 3 | **M4 入库与库存闭环** | 收货生成批次、四态台账、FIFO 出库、调拨/ASN；审核批次与台账守恒、并发幂等、C-5 拆批和短少。 | 依赖商品及采购基础；现有 FIFO 只是内部服务，先复用并补缺口，不从头重做。 |
| 4 | **M5 订单和退货**，与 M4 联调 | 订单导入/状态、部分妥投、退货 A/B/C 和 FIFO 红冲；审核跨站、重传、多次退货、成本赔偿 C-2/C-2b。 | 不必等 M4 所有页面做完；有可用入口即可接 M1 站点权限。M9 未确认的平台字段先留待核对。 |
| 5 | **M6 账单、费用与对账** | 周/月账单导入、差异与争议、费用字典和回款；审核幂等、未匹配、截止时间及费用不重算。 | 依赖订单/退货标识与费用资料；可在阶段 4 稳定接口后并行。 |
| 6 | **M7 利润与报表** | 结合订单、FIFO 成本和账单费用，交付 L1/L2、三档口径、快照；审核 C-3、历史重算及不重复计费。 | 依赖阶段 3–5 的可信数据与版本化参数/汇率。 |
| 7 | **M8 补货与预警** | 按站点计算建议、人工确认和转采购/调拨；审核公式、在途与转单追溯。 | 依赖商品、库存、销量与采购；可在相关数据稳定后与阶段 6 并行。 |
| 贯穿 | **M9 Noon 集成和数据导入** | 先按已有授权做只读与 CSV/人工通道；获取可信样本后再做事件适配。审核来源、隐私、字段/编号和幂等。 | 无真实样本时不阻塞隔离环境业务开发；不创建导出任务或写店铺，除非另获授权。 |
| 后续 | **M10 AI 建议与审批** | 业务成熟后接只读视图、AI 草稿、独立角色及人工审批；审核隔离、权限与审计。 | 依赖相关业务入口、权限及用户已定的 AI 审批边界；具体角色按功能接入时配置。 |
| 收尾 | **跨模块验收与部署准备** | 按需求的 C-2/C-2b/C-3/C-5 案例串联测试，核对真实权限、历史数据和升级迁移，列出未完成事项。 | 完整应用及真实对接另行验证；是否部署、店铺写入不因本计划自动授权，远程推送由用户操作。 |

**当前建议从阶段 1 开始**：先盘点 M2 已有表和代码，完成 SKU、站点/仓库及 Partner SKU 最小闭环；WorkBuddy 在分配豆包前写明接口和文件归属。此阶段交付后请 Codex 审核，再推进阶段 2；库存等已写好的代码保留并按接口持续联调。

## 开发与审核流程

1. WorkBuddy 为主开发与协调，按实际情况通过豆包 CLI 交付清晰、范围有限的任务；明确模块、负责文件、输入输出、验收和不得触碰范围，防止双方同时改相同文件。豆包提交结果给 WorkBuddy，后者整合并测试；无法直接调用时再用共享记录交接。
2. 一个模块或可独立验收的关键流程完成时，WorkBuddy 在 `docs/agent-collaboration.md` 留简短审核请求：模块与基线、变更及接口、测试命令/结果与证据、未完成项及需要 Codex 判定的问题。然后由用户通知 Codex 审核；不需要每次小改都唤醒 Codex。
3. Codex 独立检查关键规则、模块接口和适当测试，按“必须修改 / 建议优化”记录问题、证据与通过条件。WorkBuddy 与豆包修复或说明，Codex 再复核；修复过程可直接沟通，协作文件只留关键决定、状态和结果。
4. 审核结论分“通过 / 有条件通过 / 未通过”，写明验证范围和未测边界；示例、单元测试或内部服务通过不等于整个模块上线。真实生产访问、部署和店铺写操作按用户授权范围办理；远程 Git 推送由用户自行操作。
5. 开工前读 `AGENTS.md` 与协作入口；保留彼此未提交改动和凭据保密。模块编号为规划编号；正式 Maven 业务模块当前为 `yxerp-noon`，无需机械拆成十个工程。

6. 从 M4 及后续模块开始，一般情况下必须实际运行若依代码生成器生成前端和后端骨架，再结合现有模块、接口、权限及业务规则调整并测试；只沿用旧骨架或手写代码不能代替本次生成。生成前核对范围，避免覆盖已有代码。对于确实用不了，或生成器不适合具体开发内容的部分，可以不使用生成器；交付时说明具体原因、生成范围、沿用和手写范围及验证结果，不必为此暂停已授权工作等待用户批准。
